# Switchboard decisions

- MongoDB stores conversation and message state. Unique indexes scope contacts, Pigeon events, inbound IDs and reply references by workspace and reset generation. The inbox sorts by latest message activity and the history sorts by provider time with a stable tie-breaker. During upgrade, existing conversations get activity timestamps from their latest stored messages.
- A reply is also its pending delivery record. Workers use recoverable MongoDB leases and derive the provider idempotency key from the stored message ID. A stale lease cannot update work reclaimed by a newer worker. A status webhook can confirm delivery before the HTTP response arrives. The first terminal status wins. Redis coordinates per-workspace sends and atomically extends the Retry-After cooldown so a shorter response cannot cut it short.
- Login uses IdP discovery, S256 PKCE, one-time state bound to an HttpOnly cookie, and a nonce verified against a signed RS256 ID token. Shared Redis sessions expire by the ID token expiry. Logout revokes the Redis session across instances. Open sockets recheck sessions every five seconds. Membership changes at the IdP take effect when the user signs in again or their session expires.
- Agents and admins can read, claim, and reply within their own workspaces. Agents can close or reopen a thread they hold or an unassigned thread, while admins can change any thread in their workspace. Closing preserves the assignment and does not block replies or reopen on inbound traffic. Offset pagination can shift when new messages arrive.
- Inbox mutations store pending events in the same MongoDB document update. A background publisher appends to Redis Streams atomically with deduplication and sequence assignment. Sockets use one cursor for replay and live reads. A reset clears inbox data, rate limits and replay history while preserving active sessions and sequence counters. Records from before this release have no historical WebSocket events.
- Redis Streams retain events and publication IDs until grader reset. Their durability across Redis crashes depends on Redis persistence. Polling and retention are sized for this assessment, with no automatic trimming. Pigeon can forget idempotency keys when it resets, and a provider send it already accepted may finish after an application reset.
- The React dashboard uses workspace-scoped HTTP reads for the inbox and message history. WebSocket events invalidate those reads, which keeps replay and live updates on the same data path without appending duplicate rows. Resume cursors and reply drafts are kept per workspace in memory for the current dashboard session. Contact and status filters cover the loaded inbox pages. Billing, Elasticsearch and encrypted notes remain outside scope.

## Phase 3 verification

- The first Linux container run scored 11/14 on Level 2 and 22/22 on Level 3. It used a Windows bind mount for runtime files and routed simulator callbacks through the Windows host. It stored 34/171 crash-window inbound messages and recovered all 12 accepted replies. The unchanged application scored 36/36 on a repeat using the Linux filesystem and Pigeon on loopback. Level 2 stored 172/172 inbound messages and recovered 12/12 accepted replies. The initial inbound failure did not reproduce in that setup.
- The focused suite reproduced a shorter Retry-After replacing a longer cooldown. The Redis change fixed that failure. The other focused cases cover raw-body signatures and ignored events, ambiguous carrier acceptance across SIGKILL, terminal statuses and recovery of a partially published event batch.
- The final Linux full check scored 75/75 across Levels 1, 2, 3 and 5. Level 2 recovered 180/180 inbound messages and 12/12 accepted replies. Level 3 recovered 12/12 accepted replies within 60 seconds after a worker died permanently, with zero duplicate deliveries. See [CHECK_REPORT.json](CHECK_REPORT.json) for the checker output. The private Level 4 checker was unavailable.
- Inbound recovery after a prolonged outage is bounded by Pigeon's finite retry schedule. Reply recovery assumes shared MongoDB and Redis are reachable and the provider resumes accepting requests.
